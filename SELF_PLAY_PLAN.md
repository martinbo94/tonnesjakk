# Self-Play Improvement Loop for Tonnesjakk NNUE

## Overview

This document describes a practical self-play improvement loop for training
successively stronger NNUE networks. The core idea: use the current best NNUE
to generate training data, train a new NNUE on that data, and only promote it
if it demonstrably beats the previous version.

```
                  +------------------+
                  |  Generation 0    |
                  |  Heuristic data  |
                  +--------+---------+
                           |
                           v
                  +------------------+
                  |  Train NNUE v0   |
                  +--------+---------+
                           |
            +--------------+--------------+
            |                             |
            v                             v
  +------------------+          +------------------+
  | Self-play with   |          | Gatekeeper match |
  | NNUE v0 to       |          | v0 vs heuristic  |
  | generate data    |          | (must pass)      |
  +--------+---------+          +------------------+
           |
           v
  +------------------+
  | Train NNUE v1    |
  +--------+---------+
           |
           v
  +------------------+
  | Gatekeeper match |  <-- v1 must beat v0 by >55% win rate
  | v1 vs v0         |
  +--------+---------+
           |
           | (pass)           (fail) --> discard v1, adjust params, retry
           v
  +------------------+
  | v1 is new best   |
  | Repeat cycle...  |
  +------------------+
```

## Phase 0: Establish Baseline (Generation 0)

The first NNUE is trained on data generated by the heuristic engine, which
runs at ~500K nodes/sec and produces high-quality positional evaluations.

### Commands

```bash
# Activate environment
.venv\Scripts\activate

# Step 1: Generate baseline training data (heuristic, depth 8)
python -m tonnesjakk.nnue --games 10000 --depth 8 --random-moves 4 ^
    --save-data gen0_data.npz --no-compare --no-history --arch 64 32

# Step 2: Train Gen 0 NNUE
python -m tonnesjakk.nnue --load-data gen0_data.npz --arch 64 32 ^
    --epochs 80 --output nnue_gen0 --no-compare --no-history

# Step 3: Validate Gen 0 against heuristic
python -m tonnesjakk.nnue --compare nnue_gen0/nnue_weights.json heuristic ^
    --compare-games 50 --depth 5
```

**Success criterion for Gen 0**: NNUE must score >= 50% vs heuristic at depth 5.
If it fails, increase training data (20K games) or search depth (9-10) before
proceeding.

### What we know from history

From `nnue_history.json`:
- Gen 1 (10K games, depth 8, 144 features): +275 ELO vs heuristic -- strong
- Gen 2 (10K games, depth 6, 157 features): -139 ELO vs heuristic -- too shallow
- Gen 3 (10K games, depth 9, 157 features): +7 ELO vs heuristic -- draws dominate

**Key lesson**: Depth matters enormously. Depth 6 produces inferior data compared
to depth 8+. Prefer higher depth with fewer games over lower depth with more games.

## Phase 1: Self-Play Generations (Generation 1+)

Each generation uses the current best NNUE to generate training data, trains
a new network, then validates it via gatekeeper matches.

### Generation N Pipeline

```bash
# Step 1: Generate data using current best NNUE
python -m tonnesjakk.nnue --games 10000 --depth 5 --random-moves 5 ^
    --use-nnue nnue_best/nnue_weights.json ^
    --save-data genN_data.npz --no-compare --no-history --arch 64 32

# Step 2: Train new candidate
python -m tonnesjakk.nnue --load-data genN_data.npz --arch 64 32 ^
    --epochs 80 --output nnue_candidate --no-compare --no-history

# Step 3: Gatekeeper match - candidate vs current best
python -m tonnesjakk.nnue --compare nnue_candidate/nnue_weights.json ^
    nnue_best/nnue_weights.json --compare-games 50 --depth 5

# Step 4: Also check candidate vs heuristic (regression test)
python -m tonnesjakk.nnue --compare nnue_candidate/nnue_weights.json ^
    heuristic --compare-games 30 --depth 5
```

### Promotion Decision

After the gatekeeper match, apply these rules:

| Candidate win rate vs best | Action |
|---|---|
| >= 55% | **Promote**: copy candidate to `nnue_best/` |
| 50-55% | **Marginal**: run 50 more games for confidence. Promote if combined >= 53% |
| 45-50% | **No improvement**: discard candidate |
| < 45% | **Regression**: discard, investigate cause |

**Additionally**: if candidate loses to heuristic (< 45% win rate), discard
regardless of performance vs previous NNUE. This prevents mode collapse where
successive generations become "specialized" against each other but worse overall.

### Promotion Commands

```bash
# If candidate passes gatekeeper:
mkdir nnue_genN
copy nnue_candidate\nnue_weights.json nnue_genN\nnue_weights.json
copy nnue_candidate\nnue_weights.json nnue_best\nnue_weights.json
```

## The Speed Problem

NNUE evaluation is significantly slower than heuristic evaluation:

| Evaluator | Approx. nodes/sec | Depth 5 game time |
|---|---|---|
| Heuristic | ~500K | ~0.5s |
| NNUE 64x32 | ~100K | ~2.5s |
| NNUE 32x16 | ~200K | ~1.3s |
| NNUE 16x8 | ~350K | ~0.7s |

This means a 10,000-game dataset at depth 5 takes roughly:

- Heuristic: ~1.5 hours
- NNUE 64x32: ~7 hours
- NNUE 32x16: ~3.5 hours

### Strategy Options (Ranked by Practicality)

#### Option A: Hybrid Data Generation (Recommended)

Use the heuristic for speed but the NNUE for knowledge. Specifically:

1. **Generate games with heuristic** at depth 8 (fast, ~500K nps)
2. **Re-evaluate positions with NNUE** (batch evaluation, no search tree)
3. **Train NNUE** to predict the NNUE re-evaluation scores

This gets the diversity benefit of deep heuristic search with the evaluation
quality of the NNUE. It requires a small code addition to re-evaluate positions
from saved `.npz` data with an NNUE engine.

**Approximate time**: ~2 hours for 10K games at depth 8 + ~10 min for re-eval.

> Note: This option requires a new `--re-evaluate` feature in `nnue.py` that
> loads an `.npz` file, replaces labels with NNUE evaluations, and saves a new
> `.npz` file. This is straightforward to implement.

#### Option B: Lower Depth with NNUE (Simple, Current Support)

Use the NNUE at depth 4-5 for data generation instead of depth 8:

```bash
python -m tonnesjakk.nnue --games 10000 --depth 5 --random-moves 5 ^
    --use-nnue nnue_best/nnue_weights.json ^
    --save-data genN_data.npz --no-compare --arch 64 32
```

The NNUE's pattern recognition partially compensates for shallower search.
A depth-5 NNUE search may play as well as a depth-7 heuristic search.

**Approximate time**: ~7 hours for 10K games at depth 5 with 64x32.

**Risk**: If the NNUE has systematic blind spots, low depth amplifies them.

#### Option C: Smaller Network for Data Generation

Train a small 16x8 "teacher" NNUE that runs at ~350K nps, use it for data
generation at depth 7, then distill into the final 64x32 network:

```bash
# Generate with fast 16x8 network
python -m tonnesjakk.nnue --games 15000 --depth 7 --random-moves 5 ^
    --use-nnue nnue_16x8/nnue_weights.json ^
    --save-data genN_fast_data.npz --no-compare --arch 16 8

# Train full-size network on that data
python -m tonnesjakk.nnue --load-data genN_fast_data.npz --arch 64 32 ^
    --epochs 80 --output nnue_candidate --no-compare
```

**Approximate time**: ~3 hours for 15K games at depth 7.

#### Option D: Time-Based Search (Requires Engine Changes)

Add a `search_timed(board, milliseconds)` method to the Rust Engine that uses
iterative deepening with a time cutoff. This gives equal "thinking time" to
both NNUE and heuristic, letting each reach its natural depth.

Currently **not supported** -- the Python Engine API only exposes `search(board, depth)`
and `search_iterative(board, max_depth)` with no time limit. Implementing this
would require:

1. Adding a `start_time` and `time_limit_ms` field to `BitBoardEngine`
2. Checking elapsed time in the search loop (every N nodes)
3. Exposing `search_timed(board, ms)` in the Python bindings

This is the most principled approach for comparison matches (equal time controls)
but not strictly necessary for data generation.

### Recommendation

Start with **Option B** (lower depth with NNUE) since it works today with no
code changes. If self-play generations plateau, switch to **Option A** (hybrid)
after implementing the re-evaluation feature. Option C is a good middle ground
if you want faster generation without code changes.

## Recommended Parameters

### Data Generation

| Parameter | Gen 0 (Heuristic) | Gen 1+ (NNUE self-play) |
|---|---|---|
| Games | 10,000 | 10,000 |
| Search depth | 8 | 5 (NNUE compensates) |
| Random opening moves | 4 (range: 2-6) | 5 (range: 3-7) |
| Max moves per game | 100 | 50 (shorter = less noise) |
| Labels | Search scores | Search scores |
| Augmentation | Horizontal flip (2x) | Horizontal flip (2x) |

**Why more random moves for self-play**: NNUE self-play tends to converge on
a narrow set of openings faster than heuristic play. More randomness in the
opening keeps the training data diverse.

### Training

| Parameter | Value | Notes |
|---|---|---|
| Architecture | 64x32 | Best quality/speed tradeoff per benchmarks |
| Epochs | 80 | Monitor val_loss; stop earlier if converged |
| Learning rate | 0.001 (Adam) | Default; consider cosine annealing |
| Batch size | 256 (default) | Works well with 200K-400K positions |
| Validation split | 10% | Default in train_model() |

### Gatekeeper Matches

| Parameter | Value | Notes |
|---|---|---|
| Games | 50 (initial), then 50 more if marginal | ~55% needed for significance |
| Search depth | 5 | Deep enough to differentiate, fast enough to complete |
| Random openings | 2-4 (default in compare_nnue) | Ensures variety |
| Max moves per game | 50 (after Fixer's patch) | Prevents infinite games |

## Avoiding Mode Collapse and Training Pitfalls

### Problem 1: Echo Chamber Effect

When a network only trains on its own games, it can develop blind spots. If the
NNUE consistently misses a particular tactical pattern, it will never appear in
the training data, so the next generation will miss it too.

**Mitigations**:
- Always validate against the heuristic (catches known-pattern regressions)
- Mix in 25% heuristic-generated data with 75% self-play data:
  ```bash
  # Generate heuristic data
  python -m tonnesjakk.nnue --games 2500 --depth 8 ^
      --save-data genN_heuristic.npz --no-compare --arch 64 32

  # Generate NNUE data
  python -m tonnesjakk.nnue --games 7500 --depth 5 ^
      --use-nnue nnue_best/nnue_weights.json ^
      --save-data genN_nnue.npz --no-compare --arch 64 32
  ```
  Then combine datasets before training (requires a small utility or numpy
  script to concatenate two `.npz` files).

### Problem 2: Opening Diversity Collapse

Self-play engines tend to converge on a small set of "optimal" openings, reducing
position diversity and making the NNUE fragile to unusual positions.

**Mitigations**:
- Use `--random-moves 5` (range 3-7) for wider opening variety
- Vary random_moves between generations (4, then 6, then 5, etc.)
- Monitor the number of unique positions in training data; if it drops, increase
  randomness

### Problem 3: Draw Bias

From the training history, Gen 3 produced 49/50 draws at depth 5. If the NNUE
plays "too safely", it will generate training data dominated by drawn positions,
teaching the next generation to also play for draws.

**Mitigations**:
- Use search scores (not game outcomes) for labels -- this preserves evaluation
  nuance even in drawn games
- If draw rate exceeds 70% in data generation, try:
  - More random opening moves (6-8)
  - Asymmetric positions (3 random moves for White, 5 for Black)
  - Temperature: randomly select from top-3 moves instead of always best move
    (requires a code change to `play_game()`)

### Problem 4: Overfitting to Data Generation Depth

A network trained on depth-5 search scores learns to predict depth-5 evaluations.
If you later compare it at depth 7, the evaluations it learned may be
systematically biased.

**Mitigations**:
- Match comparison depth to training data depth when possible
- When changing depth between generations, re-train from combined data rather
  than only new data

## Success Criteria: When to Stop Iterating

The self-play loop should stop when marginal returns diminish. Specifically:

### Keep Iterating When

- Each new generation improves by >= +20 ELO vs the previous best
- New generation consistently beats heuristic at equal depth
- Training loss is still decreasing with more data/epochs

### Stop Iterating When

- Two consecutive generations fail the gatekeeper (no improvement)
- ELO gains drop below +10 per generation
- Performance vs heuristic stops improving (ceiling reached)
- You have exhausted the parameter space (tried more data, deeper search,
  different architectures)

### Ultimate Success

The NNUE project can be considered successful when:

1. **NNUE beats heuristic at equal time**: At the same thinking time per move
   (e.g., 100ms), NNUE wins >= 55% of games. This tests whether NNUE's superior
   evaluation compensates for its slower speed.

2. **NNUE beats heuristic at equal depth**: At depth 5-6, NNUE wins >= 60%
   of games. This tests pure evaluation quality.

3. **Successive generations improve**: At least 3 generations of self-play
   improvement, each passing the gatekeeper.

## Practical Iteration Schedule

Here is a concrete schedule for the first 5 generations:

### Generation 0 (Baseline)
```bash
python -m tonnesjakk.nnue --games 10000 --depth 8 --random-moves 4 ^
    --save-data gen0_data.npz --no-compare --arch 64 32
python -m tonnesjakk.nnue --load-data gen0_data.npz --arch 64 32 ^
    --epochs 80 --output nnue_gen0 --no-compare
python -m tonnesjakk.nnue --compare nnue_gen0/nnue_weights.json heuristic ^
    --compare-games 50 --depth 5
# Expected: >= 55% vs heuristic
# Copy to nnue_best/ if passes
```

### Generation 1 (First Self-Play)
```bash
python -m tonnesjakk.nnue --games 10000 --depth 5 --random-moves 5 ^
    --use-nnue nnue_best/nnue_weights.json ^
    --save-data gen1_data.npz --no-compare --arch 64 32
python -m tonnesjakk.nnue --load-data gen1_data.npz --arch 64 32 ^
    --epochs 80 --output nnue_gen1 --no-compare
python -m tonnesjakk.nnue --compare nnue_gen1/nnue_weights.json ^
    nnue_best/nnue_weights.json --compare-games 50 --depth 5
python -m tonnesjakk.nnue --compare nnue_gen1/nnue_weights.json ^
    heuristic --compare-games 30 --depth 5
# Promote if >= 55% vs gen0 AND >= 50% vs heuristic
```

### Generation 2 (With Heuristic Mixing)
```bash
# 75% self-play data
python -m tonnesjakk.nnue --games 7500 --depth 5 --random-moves 5 ^
    --use-nnue nnue_best/nnue_weights.json ^
    --save-data gen2_nnue.npz --no-compare --arch 64 32
# 25% heuristic data
python -m tonnesjakk.nnue --games 2500 --depth 8 --random-moves 4 ^
    --save-data gen2_heur.npz --no-compare --arch 64 32
# Combine and train (requires merge script, see below)
python merge_datasets.py gen2_nnue.npz gen2_heur.npz gen2_data.npz
python -m tonnesjakk.nnue --load-data gen2_data.npz --arch 64 32 ^
    --epochs 80 --output nnue_gen2 --no-compare
# Gatekeeper as before
```

### Generations 3-4 (Refinement)
Same as Generation 2, but adjust parameters if improvement stalls:
- If draw rate > 70%: increase `--random-moves` to 6
- If ELO gain < +10: try `--depth 6` (slower but deeper)
- If training loss plateaus: increase `--epochs` to 120

## Dataset Merging Utility

For mixing heuristic and self-play data, a small script is needed:

```python
# merge_datasets.py
import numpy as np
import sys

def merge(file_a, file_b, output):
    a = np.load(file_a)
    b = np.load(file_b)
    X = np.concatenate([a['X'], b['X']])
    y = np.concatenate([a['y'], b['y']])
    # Shuffle
    perm = np.random.permutation(len(X))
    np.savez_compressed(output, X=X[perm], y=y[perm])
    print(f"Merged {len(a['X'])} + {len(b['X'])} = {len(X)} positions -> {output}")

if __name__ == "__main__":
    merge(sys.argv[1], sys.argv[2], sys.argv[3])
```

## When Heuristic Data Might Be Better

Self-play is not always superior to heuristic-generated data. Consider sticking
with heuristic data generation when:

1. **The NNUE is still weak**: A weak NNUE generates weak training data. Until
   Gen 0 beats the heuristic at equal depth, self-play will produce worse data
   than the heuristic.

2. **Speed matters more than quality**: For architecture experiments (comparing
   64x32 vs 32x16 vs 16x8), you want fast data generation. Use a single
   high-quality heuristic dataset and train all architectures on it.

3. **Debugging evaluation issues**: If an NNUE generation shows regressions
   (worse vs heuristic), generating fresh heuristic data at high depth provides
   a known-good baseline to retrain from.

4. **Diminishing returns from self-play**: If three consecutive self-play
   generations show < +10 ELO improvement, the NNUE has likely extracted most
   value from its own play style. At this point, improvements must come from
   architectural changes (wider layers, more features, skip connections) or
   training methodology (learning rate schedules, loss functions), not more
   self-play data.

**Rule of thumb**: Use heuristic data until NNUE beats heuristic by >= +50 ELO
at equal depth. Only then switch to self-play data generation.

For each generation:

- [ ] Generate training data (self-play or heuristic)
- [ ] Save data with `--save-data genN_data.npz` for reproducibility
- [ ] Train candidate model with `--output nnue_genN`
- [ ] Gatekeeper match: candidate vs current best (50 games, depth 5)
- [ ] Regression test: candidate vs heuristic (30 games, depth 5)
- [ ] If promoted, copy to `nnue_best/nnue_weights.json`
- [ ] Record results in `nnue_history.json`
