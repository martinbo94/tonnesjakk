# NNUE Training Plan — 2026-02-12

## Goal

Train an NNUE that beats the heuristic at equal time controls.
Once achieved, begin bootstrapping: use the NNUE for self-play data to train
progressively stronger models.

## Current State

- Pipeline improvements implemented: sigmoid normalization (`tanh(score/600)`),
  quiet position filtering, lambda blend, 13 relational features
- Gen1 model (old): +275 ELO at equal depth 5, but **0-6 at equal time** (200ms)
  because NNUE is ~5x slower per node (depth 5 vs depth 10)
- No model has been trained with the new pipeline yet
- Existing data file `training_d7.npz` has 7.7M positions at depth 7 but uses
  old /1000 linear normalization — would need rescaling or just regenerate

## How to Compare: Time Controls

There's no single "correct" time control — different time budgets test different
things. We should test at multiple and find the **crossover point** where NNUE
starts winning.

| Time control | What it tests | Expected behavior |
|-------------|--------------|-------------------|
| 50ms/move | Pure speed (NNUE ~depth 3-4) | Heuristic likely wins big |
| 200ms/move | Moderate (NNUE ~depth 5-6) | Target for "good enough" |
| 500ms/move | Deeper (NNUE ~depth 7-8) | Eval quality starts to matter |
| 1000ms/move | Deep (NNUE ~depth 8-9) | NNUE should dominate if eval is good |

**The crossover time is the key metric.** If NNUE wins at 500ms but loses at
200ms, we know the eval is better than heuristic but NPS is the bottleneck.
If NNUE loses even at 1000ms, the eval itself needs work.

For bootstrapping, the NNUE just needs to beat heuristic at *some* reasonable
time control. Even winning at 1000ms is fine — it means the NNUE produces better
self-play data when given enough thinking time, which feeds the next generation.

We can also compare at **equal depth** as a pure eval quality test (removes
speed from the equation), but the equal-time tests are what matter for practical
strength.

## Phase 1: First Competitive NNUE

### Step 1 — Generate heuristic self-play data

This is the most time-consuming step. The engine plays thousands of games
against itself using the heuristic eval, recording every position + search score.
More games = more training data = better model, but takes longer.

**Time estimates for data generation (8 workers):**

| Games | Depth | Est. time | Est. positions |
|-------|-------|-----------|----------------|
| 5,000 | 5 | ~10 min | ~200K-400K |
| 10,000 | 5 | ~20 min | ~400K-800K |
| 5,000 | 7 | ~45 min | ~200K-400K |
| 20,000 | 7 | ~3 hours | ~800K-1.5M |

Start small, scale up if the model isn't strong enough.

```bash
.venv\Scripts\python.exe -m tonnesjakk.nnue --games 5000 --depth 5 --lambda 1.0 --workers 8 --save-data training_gen1_d5.npz --generate-only
```

- **Why depth 5?** Fast, and the search scores at depth 5 already encode
  tactical knowledge the NNUE can learn to approximate in a single eval call.
- **Why lambda=1.0?** Pure search scores for gen 1. The heuristic search at
  depth 5 produces reliable positional assessments. Game outcomes add noise
  when the eval function (heuristic) is already decent.
- **Why --generate-only?** Separates data generation from training so we can
  regenerate data or retrain without repeating the slow step.
- **Note:** Data generation is Ctrl+C safe — it saves progress periodically.

### Step 2 — Train the model

```bash
.venv\Scripts\python.exe -m tonnesjakk.nnue --load-data training_gen1_d5.npz --epochs 50
```

- Produces `nnue_weights.json`
- Check training loss — should drop below 0.02 for a good fit

### Step 3 — Find the crossover point

Test at multiple time controls to understand where the NNUE's eval quality
starts to outweigh its speed disadvantage.

```bash
.venv\Scripts\python.exe scripts\test_model.py nnue_weights.json --time-ms 100 --games 30
.venv\Scripts\python.exe scripts\test_model.py nnue_weights.json --time-ms 200 --games 30
.venv\Scripts\python.exe scripts\test_model.py nnue_weights.json --time-ms 500 --games 30
.venv\Scripts\python.exe scripts\test_model.py nnue_weights.json --time-ms 1000 --games 30
```

Also test at equal depth to isolate eval quality from speed:

```bash
.venv\Scripts\python.exe -m tonnesjakk.nnue --compare nnue_weights.json heuristic --compare-games 50 --depth 5
```

**Interpreting results:**
- Wins at equal depth but loses at all time controls → eval is better but too slow
- Wins at 1000ms, loses at 200ms → eval is good, NPS is the bottleneck
- Wins at 200ms → ready for bootstrapping
- Loses at equal depth → eval itself needs improvement (more/deeper data)

**If it fails**, try these adjustments (in order):
1. More data: increase to 10K or 20K games
2. Deeper data: depth 7 instead of 5 (slower but richer search scores)
3. Lambda blend: try --lambda 0.85 to mix in game outcomes
4. Without relational features: --no-relational (faster NPS, less eval info)

## Phase 2: Bootstrapping

Once we have a model that beats heuristic at any reasonable time control
(even 1000ms is fine — it still means the NNUE produces better evaluations):

### Gen 2 — NNUE self-play

```bash
.venv\Scripts\python.exe -m tonnesjakk.nnue --games 10000 --depth 5 --lambda 0.85 --workers 8 --nnue-path nnue_weights.json --save-data training_gen2.npz
```

- Self-play with the gen 1 NNUE generates higher-quality positions
- Lambda=0.85 now makes sense: the NNUE search scores + game outcome correction
- Train on this data, test again, repeat

### Gen 3+ — Deeper search, more data

- Increase depth to 7 as models get stronger
- Increase games to 20K+
- Each generation should be tested against the previous one AND heuristic
- Stop when improvement plateaus

## Key Metrics to Track

| Metric | How | What it tells us |
|--------|-----|-----------------|
| Crossover time | Test at 100/200/500/1000ms | Lowest time control where NNUE wins |
| Win rate at equal depth 5 | `--compare --depth 5` | Pure eval quality (ignoring speed) |
| NNUE avg depth at 200ms | Shown in test output | How much depth NNUE gets in practice |
| Win rate vs previous gen | `--compare` two models | Whether bootstrapping is working |
| Training loss | Printed during training | Fit quality (target: <0.02) |
| Positions generated | Printed during data gen | Data quantity (aim for 200K+) |

## Potential Issues

1. **NPS too low**: If NNUE only reaches depth 4-5 at 200ms, the eval advantage
   can't compensate. Investigate if relational features are too expensive.
   Fallback: try without relational features (--no-relational) to see if NPS
   matters more than eval quality.

2. **Training data too homogeneous**: Heuristic self-play may produce repetitive
   positions. Mitigation: the random opening phase (2-4 random moves) helps,
   but we could increase to 4-6 if needed.

3. **Eval doesn't generalize**: Low training loss but poor play. Could mean
   overfitting to heuristic quirks. Fix: add lambda<1.0 game outcome blending,
   or use deeper search data.
